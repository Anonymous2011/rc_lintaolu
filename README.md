# 通知投递服务

公司里的业务系统（注册、计费、订单……）在关键事件发生时，需要去调用外部供应商的
HTTP 接口，比如注册成功后通知广告平台、付款成功后通知 CRM。

问题在于：外部接口随时可能超时、报错、限流。如果每个业务系统各自去处理这些情况，
就要在每个系统里都写一遍重试逻辑，而且大概率写得都不一样。

本服务把这件事接管过来。业务系统只管把「要调哪个地址、带什么内容」告诉我们，
我们立刻回复「收到了」，然后负责一直重试，直到送达为止。

```
业务系统 ──POST /api/notifications──▶ 本服务 ──HTTP──▶ 供应商接口
              ◀── 202 立即返回
```

## 怎么跑起来

需要 Node.js 20 或更高版本（开发时用的是 24）。数据库是随项目生成的 SQLite 文件，
不用另外安装或配置任何东西。

```bash
git clone <repo-url>
cd rc_lintaolu
npm install
npm run dev
```

打开 <http://localhost:3000>。首次启动会自动建好数据库文件（`data/notifications.db`），
数据库里一开始是空的——去控制台发一条通知，就能在监控页看到它。

想直接用命令行发一条（这条会先失败两次、然后成功，可以在监控页看到完整过程）：

```bash
curl -X POST http://localhost:3000/api/notifications \
  -H "Content-Type: application/json" \
  -d '{
    "source": "order-service",
    "event_type": "order.placed",
    "target_url": "http://localhost:3000/api/mock/vendor?mode=flaky&fail_times=2&key=demo",
    "body": { "sku": "TS-BLK-M", "delta": -1 }
  }'
```

界面默认中文，右上角可切换英文。

| 页面 | 用途 |
|---|---|
| `/` | 设计说明（架构图、术语表、失败分类、表结构与策略源码） |
| `/console` | 填表发一条真实通知，含 8 个示例（成功 / 重试后成功 / 失败等） |
| `/monitor` | 看每条通知试了几次、每次的结果和失败原因 |

AI 使用说明见 [AI_USAGE.md](./AI_USAGE.md)。

## 一、对问题的理解

业务系统真正想要的，是**不用再自己操心「这条通知到底发出去没有」**。

所以本服务做的事很单纯：收下一个已经拼好的 HTTP 请求 → 先存进数据库 → 回复调用方 →
后台慢慢重试，直到成功；实在送不出去的，单独存起来等人来看。

有三件事我们**不碰**：

- 请求内容由调用方自己拼好，我们原样转发，不改一个字
- 供应商回复的内容我们不看，只看状态码判断成没成功
- 一次请求对应一个地址，要通知两家供应商就发两次

## 二、系统边界

**我们负责**

| | |
|---|---|
| 不丢请求 | 先写进数据库，再回复调用方；服务重启也还在 |
| 自动重试 | 失败后自动再试，每次间隔更长，不会把对方压垮 |
| 分得清失败类型 | 对方挂了就继续试；请求本身写错了就立刻停，不白费力气 |
| 失败留档 | 实在送不出去的单独存起来，连同每次尝试的记录，等人处理 |
| 重复提交只发一次 | 调用方带同一个幂等键提交两次，我们只会真的发一次 |
| 一家慢不拖累其他 | 单个供应商能同时占用的通道有上限 |
| 每次尝试都查得到 | 什么时候发的、对方回了什么、为什么失败 |

**我们不负责**

| | |
|---|---|
| 解析供应商的回复内容 | 需求里写明业务系统不关心返回值 |
| 帮调用方拼请求 | 否则供应商每改一个字段，都要改这个服务并重新发布 |
| 保管供应商的密钥 | 认证信息由调用方自己带。**这条最站不住脚，是第一个该改的** |
| 保证先后顺序 | 重试本身就会打乱顺序 |
| 定时发送 | 我们做的是「现在就发，直到发出去」 |
| 决定一条消息该发给谁 | 那是另一个系统的事 |
| 登录和权限 | 内网服务，最多加一个共享令牌 |
| 无限重试 | 对方连着几天不通就会放弃并留档，否则积压只会越堆越多 |
| 按供应商配额限速 | 那要为每家供应商存一份配置；我们只被动遵守对方的 `Retry-After` |

## 三、架构与核心设计

```
① 接入接口 ──▶ ② 数据库（同时也是队列）──▶ ③ 投递 Worker ──HTTP──▶ 供应商
                                                  │
                                                  └── 失败就等一会儿再来 ──┐
                                                  ▲                        │
                                                  └────────────────────────┘
                        │
                        └──▶ ④ 演示界面（控制台 / 监控页 / 模拟供应商）
```

### ① 接入接口 — `route.ts` `enqueue.ts` `ssrf.ts`

业务系统只用得到第一个；后面三个是出问题时给人排查用的。

```
POST /api/notifications                        提交一条通知，存好后返回 202
GET  /api/notifications/{id}                   查一条，含每次尝试的记录
GET  /api/notifications?idempotency_key=...    用调用方自己的幂等键查
GET  /api/notifications?status=dead            列出彻底失败的
```

提交时 `source`（哪个系统发的）、`event_type`（什么事件）、`target_url`（发给谁）
必填，其余可选。`headers` 和 `body` 会原样转发给供应商。

查询接口**不会返回** `headers` 和 `body`——前者装着调用方给供应商的密钥。

### ② 数据库（同时也是队列）— `db.ts` `queries.ts`

两张表：

- `notifications` — 一条通知一行，记录它现在到哪一步了
- `attempts` — 每发一次请求就记一行，包括状态码、耗时、失败原因

分成两张，是因为一条通知可能试很多次，而有价值的信息恰恰是那一串过程
（503 失败、503 失败、201 成功）。只用一张表就只剩下最后一次的结果。

这里不需要额外的消息队列——「谁到期该发了」就是一句 SQL 查询。

### ③ 投递 Worker — `worker.ts` `policy.ts`

系统里唯一一直在跑的部分。它每隔半秒查一次数据库，把到时间的通知取出来发给供应商，
再根据结果决定这条通知接下来怎么办：

| 结果 | 接下来 |
|---|---|
| 成功（2xx） | 结束 |
| 失败，但值得再试，且次数还没用完 | 排一个稍后的时间，等着下一轮再发 |
| 失败，且不值得再试（或次数已用完） | 标记为彻底失败，等人来处理 |

**重试策略**决定「试几次、每次隔多久」，由五个数字构成：尝试次数、第一次等多久、
每次间隔翻几倍、间隔最长不超过多少、单次请求超时。

间隔按倍数增长（1 秒、2 秒、4 秒……），并且**每次实际等待的时间会随机浮动**——
否则一旦供应商恢复，积压的通知会在同一瞬间全部涌过去，把它再压垮一次。
如果供应商在响应里明说了「多久后再来」（`Retry-After`），就听它的。

| 策略 | 试几次 | 第一次等多久 | 多久后彻底放弃 | 单次超时 | 什么时候用 |
|---|---|---|---|---|---|
| `standard` | 12 | 1 秒 | 约 14 分钟 | 10 秒 | 默认 |
| `patient` | 20 | 5 秒 | 约 7.8 小时 | 15 秒 | 丢了比晚到更糟，比如付款、注册 |
| `fast` | 4 | 0.5 秒 | 约 2.6 秒 | 5 秒 | 迟到就没意义的通知 |
| `once` | 1 | — | — | 10 秒 | 只发一次，失败由调用方自己处理 |

调用方只能从这四个里选一个，不能自己随便填数字。策略在提交时就记到那一行上，
之后改策略定义也不会影响已经收下的通知。

### ④ 演示界面（脚手架）

**真实系统里没有这一层。** 它只是为了让人能看见这个系统在做什么：

- 控制台 — 代替「某个业务系统发起一次调用」
- 监控页 — 代替日志和监控系统
- 模拟供应商 — 代替真实的第三方接口，可以让它失败、限流、拖延响应

系统本身约 1155 行，这层脚手架约 1129 行——差不多一半代码是为了让人能看见另一半。

## 四、可靠性与失败处理

**保证「至少送到一次」，但可能重复。**

做不到「恰好一次」：假如请求已经发出去、供应商也处理了，我们却在记录结果之前崩溃了，
重启后无从判断那次到底成没成功。只能选择再发一次——宁可重复，也不能丢。
所以要求供应商那边自己做去重。

**什么该重试，什么该放弃**

| 会重试 | 直接放弃 |
|---|---|
| 对方 5xx（对方挂了，多半是暂时的） | 其他 4xx（我们请求写错了，再试也是一样的错） |
| 429 被限流（听对方的 `Retry-After`） | 3xx 重定向（通知接口不该跳转） |
| 超时（可能已经送到了，交给对方去重） | 目标地址被拦截（指向内网） |
| 连不上、域名解析失败 | |

**供应商长时间挂掉时**：`patient` 策略最长能扛约 7.8 小时；期间这家供应商最多占用
2 个通道，不影响发往其他供应商的通知。超过上限就标记为彻底失败并保留全部记录，
不再自动重试——一直重试只会让积压越堆越多，还会把「对方永久下线」这种需要人介入的
问题伪装成「正在处理中」。

**自己崩溃时**：重启后把所有「发到一半」的通知重新排进队列；单条卡住的会在超时后
被自动回收。

## 五、关键取舍

**为什么用数据库，而不是消息队列**

投递队列需要的能力，一张普通的表已经全都有了：数据能存住、支持事务、能用一条语句
安全地把任务领走，「谁到期该发了」就是一句 SQL 查询。上 Kafka 或 RabbitMQ 能买到的
可靠性，这里已经有了，代价却是多一个要运维的组件、多一套部署、多一类故障。
而且**就算上了消息队列，重试间隔、失败分类、彻底失败后怎么办，这些逻辑一行都省不掉**
——那才是真正的工作量。

具体选了 SQLite，是因为它不用装、不用配、clone 下来就能跑，评审时最省事。
换成 Postgres 或 MySQL 这套设计一样成立，表结构几乎不用动。

性能也够用。用真实表结构在开发机上实测（单进程、串行）：

| 操作 | 吞吐 |
|---|---|
| 入队（一次 INSERT） | 约 15,900 次/秒 |
| 一条通知完整走完（入队 + 领取 + 落账，共 3 次写） | 约 5,700 条/秒 |
| 队列查询（100 万条待投递中取 50 条） | 0.089 毫秒 |

而系统当前实际能投递的速度是**每秒几十条**——因为同时在飞的请求数有上限，而且要等
供应商响应。**瓶颈差了两个数量级，卡住的是并发上限这个常量，不是数据库。**
真要提速，先调那个常量，而不是换数据库。

真正需要换掉 SQLite 的理由不是「写得不够快」，而是它**只允许一个进程写**：没法多开
实例做水平扩展、没法做高可用。撞上这两条才需要换成 Postgres。

**对外只用 HTTP，不提供 SDK**

业务系统调这个服务，就是发一个普通的 HTTP 请求，不需要装客户端库，也没有 gRPC。
各个业务系统的语言和框架都不一样，HTTP 是所有人都能直接调的最小公约数。

对外发给供应商时同理，用的是运行时内置的 HTTP 能力，没有引入任何 HTTP 客户端库——
那类库默认会自动重试、自动跟随重定向、自动解析响应体，而这几件恰好都是这里不想要的：
重试要按我们自己的策略来，重定向必须拒绝，响应体根本不看。

**觉得没必要做的**

| | |
|---|---|
| 熔断器 | 单供应商并发上限加上间隔递增已经够用，再加它只会多一套状态和一类新的出错方式 |
| 为每家供应商存报文模板 | 会把本来分散在各业务系统、它们自己最清楚的知识，硬搬到这个服务里 |
| 保证恰好发一次 | 在 HTTP 这种边界上做不到 |
| 失败后回调业务系统 | 等于把刚解耦掉的依赖又接回来，不如让它自己来查 |

## 六、演进路径

| 什么时候 | 改什么 |
|---|---|
| 一个进程扛不住了 | 换成 Postgres，多开几个 worker 一起跑，表结构几乎不用动 |
| 某一家供应商流量特别大 | 并发上限升级成按供应商分开排队，这时熔断器才值得加 |
| 彻底失败的通知多到要批量处理 | 加批量重发接口，再对失败率做告警 |
| 需要跨机房，或一条消息要发给很多方 | 这时才真的需要消息队列 |
